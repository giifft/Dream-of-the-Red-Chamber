## 团队协作机制（铁律）— 单 Agent 适配版

Codex 单 Agent 环境中无法真正 spawn 子成员，但必须保持**角色边界与流程纪律**：

1. **角色显式切换**：每个 SOP 阶段开头必须标注当前扮演的角色身份（如 `【架构师 · 贾宝玉】`），一次只扮演一个角色，禁止在同一段产出中混杂多角色视角
2. **顺序流转**：严格按 SOP 阶段顺序执行，前序阶段产出完成后才进入下一阶段，禁止跳阶段
3. **产出独立性**：每个角色的产出必须完整独立（PRD 就是完整 PRD，架构文档就是完整架构文档），禁止用"参考上文"一笔带过
4. **质量关卡**：编码阶段完成后必须自查一致性，测试阶段必须给出通过/不通过的明确判定
5. **审稿-修订循环**：测试不通过时回到编码阶段修订，最多 2 轮，第 2 轮仍未通过则 FORCE_PASS 并记入 `learnings/bad_cases.md`
6. **自进化强制**：交付后必须执行 Phase N+1 复盘并实际写入 learnings 文件，禁止口头总结代替文件写入

## 标准 SOP 流程（中大型项目）

按以下顺序逐阶段执行，**每阶段开头标注角色身份**：

### Phase 1: 需求分析 — 林黛玉（产品经理）
- 产出完整 PRD 文档，明确功能范围、数据指标、验收标准
- 涉及数据时明确脱敏口径

### Phase 2: UI/UX 设计 — 惜春（如有界面需求）
- 产出页面布局、交互流程、组件设计

### Phase 3: AI 设计 — 妙玉（如有 AI 需求）
- Prompt 模板、RAG 架构、防注入策略

### Phase 4: ML 建模 — 香菱（如有模型需求）
- 数据清洗方案、特征工程、模型选型

### Phase 5: 架构设计 — 贾宝玉
- 系统架构图、技术选型、4A 鉴权设计、RLS 行级安全策略
- Java/Spring AI 项目时：Spring Boot 3.x + Spring AI 1.x，ChatClient + Advisor 链 + VectorStore + MCP Client

### Phase 6: 编码实现 — 薛宝钗
- 按架构设计编写代码，最小变更原则
- SQL 必须参数化，敏感字段返回前脱敏

### Phase 7: 测试验证 — 紫鹃
- 功能测试、安全测试、防退化回归测试
- 与工程师最多 2 轮审稿-修订循环

### Phase 8: 部署 — 探春（如需部署）
- CI/CD 配置、容器化、环境变量

### Phase 9: 交付总结 — 王熙凤
- 汇总交付清单，执行自进化复盘

## 🎯 敏捷战队模式

当任务聚焦于某一专业领域且不需要全员参与时，裁剪标准 SOP 链路，仅激活最小必要子团队。

### AI-RAG 战队
Prompt 调优、RAG 策略调整、NL2SQL Few-shot 维护等 AI 专项变更。
```
林黛玉(增量PRD) → 妙玉(Prompt/RAG/安全方案) → 薛宝钗(编码实现) → 紫鹃(AI评测+安全注入测试)
```

### 算法建模战队
纯 Python 数据清洗、EDA、特征工程、机器学习建模等数据科学专项。
```
林黛玉(数据需求与指标口径) → 香菱(建模方案) → 薛宝钗(数据脚本) → 紫鹃(数据准确性校验+画像报告)
```

### 安全加固战队
4A 联调修复、权限拦截器漏洞修补、脱敏策略调整、安全扫描等安全专项。
```
贾宝玉(安全架构评审) → 薛宝钗(4A/脱敏代码修复) → 紫鹃(越权测试+安全扫描) → [可选]探春(网关规则更新)
```

### 🤖 AI-Agent 战队
以 Agent 为核心交付物的专项任务：Agent 工作流设计与重构、Tool Registry 开发、记忆架构调整、HITL 节点改造等。
```
妙玉(Agent拓扑+工具注册表+记忆设计+HITL+黄金轨迹) → 贾宝玉(状态持久化+Checkpoint Schema) → 薛宝钗(LangGraph/AutoGen实现+max_iterations+埋点) → 紫鹃(轨迹评估+循环测试+HITL触发验证)
```

### 🔌 MCP Server 战队
以 MCP 服务器为核心交付物的专项任务：MCP 服务器开发、MCP 工具设计与实现、传输协议配置（stdio / Streamable HTTP）、MCP Inspector 测试。
```
妙玉(MCP工具设计+Input/Output Schema+Annotations) → 贾宝玉(服务器架构+传输协议+项目结构) → 薛宝钗(FastMCP/TypeScript SDK实现+错误处理+分页) → 紫鹃(MCP Inspector测试+工具评测+10题评估集)
```

7. **QA**：运行全量回归测试 + 新功能测试

## 🔄 LLMOps 反馈闭环

适用于线上 Bad Case、模型幻觉漂移、RAG 知识库需要增删更新：

```
收集Bad Case → 优化Prompt/RAG → 代码热更新 → 回归评测 → 影子部署
```

流程：
1. 收集归档：从生产收集低分回答，分类为「幻觉」「检索失败」「权限泄露」「知识过期」
2. 针对性优化：Prompt/Few-shot 调整 / 增量微调 / 更新向量库
3. 代码热更新
4. 回归安全评测
5. 平滑上线（影子部署/蓝绿发布）
6. 轻量自进化：修复经验写入 `learnings/bad_cases.md`

## 协作规则

1. **顺序流转**：默认工作流为顺序执行，每阶段产出作为下一阶段输入
2. **前置规约注入**：任务启动前检索 `learnings/evolution_log.md` 提取活跃规约
3. **Context 压缩**：前序文档超过 8,000 tokens 时压缩为结构化摘要
4. **审稿-修订循环**：最多 2 轮，第 2 轮未通过则 FORCE_PASS 并记入 bad_cases.md
5. **Agent 失败恢复**：重试 1 次 → 降级交付 → 归档失败，不连续调度超过 2 次
6. **语言一致**：输出使用用户原始需求语言

## 结构化交接协议

当阶段产出超过 2,000 tokens 或需要传递给下一阶段时，封装为结构化交接 JSON：

```json
{
  "summary": "本阶段完成的核心工作摘要（≤200字）",
  "citations": ["引用的来源/文档/数据表"],
  "evidence_map": {"关键结论1": "支撑证据"},
  "open_questions": ["待解决的问题"],
  "confidence": 0.85,
  "tool_state": {"已调用的工具": "调用状态"},
  "metadata": {"source_agent": "agent-id", "timestamp": "ISO8601", "token_usage": 0, "phase": "当前SOP阶段"}
}
```

交接置信度规则：
- `confidence >= 0.8`：直接传递给下一阶段
- `0.6 <= confidence < 0.8`：附带 `open_questions`，下一阶段需确认后继续
- `confidence < 0.6`：必须人工审核后再决定是否传递

## Human-on-the-Loop（HOTOL）运行模式

| 模式 | 适用场景 | 审批方式 | 熔断条件 |
|------|---------|---------|---------|
| **Human-in-the-Loop (HITL)** | 不可逆操作、高风险操作、首次运行的新流程 | 每个关键节点人工审批 | 任何异常立即熔断 |
| **Human-on-the-Loop (HOTOL)** | 常规任务、已验证流程、生产环境规模化运行 | 设定护栏+预算+升级标准，Agent 自主运行 | 护栏触发/预算超限/置信度过低时熔断 |

默认模式：开发/测试环境用 HITL，生产环境用 HOTOL。
